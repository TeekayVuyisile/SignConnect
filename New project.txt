Yes — **this is absolutely possible**, and I actually think your revised idea is much stronger than a simple sign-language recognition demo.

What you're describing is essentially a **real-time accessibility video-calling platform** where each participant can choose how they communicate.

### The core idea

Imagine I call you:

```text
┌──────────────────────────────────────────────────────────┐
│                    VIDEO CALL                            │
│                                                          │
│       ┌──────────────────┐    ┌──────────────────┐      │
│       │                  │    │                  │      │
│       │    YOUR VIDEO    │    │   THEIR VIDEO    │      │
│       │                  │    │                  │      │
│       │                  │    │                  │      │
│       └──────────────────┘    └──────────────────┘      │
│                                                          │
│  💬 Live captions                                        │
│  ─────────────────────────────────────────────────────   │
│  "Hello, how are you?"                                   │
│                                                          │
│  🤟 Sign translation                                     │
│  ─────────────────────────────────────────────────────   │
│  "I'm doing well, thank you."                            │
│                                                          │
│          🎤 Mute     📹 Camera     💬 Captions     ❌     │
└──────────────────────────────────────────────────────────┘
```

The really interesting part is that **both sides don't have to communicate in the same way**.

---

# The two communication pipelines

You essentially have **two independent real-time translation systems**.

### 1. Hearing person → Deaf/Hard-of-Hearing person

I speak normally:

> "Hi, are you available for the meeting tomorrow?"

Your application captures my microphone audio.

```text
Microphone
    ↓
Speech-to-Text
    ↓
"Hi, are you available for the meeting tomorrow?"
    ↓
Live subtitle
```

The deaf user sees the transcription **while you're talking**.

---

### 2. Deaf person → Hearing person

The deaf user responds using sign language.

```text
Camera
   ↓
Hand / pose detection
   ↓
Sign recognition
   ↓
"Yes, I'll be available."
   ↓
Live subtitle
```

And potentially you could eventually add:

```text
Recognized sign
      ↓
     Text
      ↓
Text-to-Speech
      ↓
🔊 "Yes, I'll be available."
```

So the hearing user doesn't even necessarily need to read the screen.

---

# And here's where your idea becomes really good

**Don't force the user to use one mode.**

Give each participant controls such as:

### Accessibility controls

**🎤 Live Transcription**

> Converts speech → text

**🤟 Sign Translation**

> Converts recognized signs → text

**🔊 Text to Speech**

> Converts typed/translated text → speech

**💬 Captions**

> Displays the other person's speech

This means the platform can support different combinations.

For example:

### Hearing → Deaf

**Hearing user**

🎤 Speaks normally

↓

**Deaf user**

💬 Sees:

> "Can you send me the document?"

---

### Deaf → Hearing

**Deaf user**

🤟 Signs:

> "Yes, I'll send it now."

↓

**Hearing user**

💬 Sees:

> "Yes, I'll send it now."

---

### Deaf → Deaf

Both users can simply use **video/sign language** without translation if they prefer.

That's important because you don't want to design the application as though Deaf people *need* translation to communicate with each other.

---

# What about latency?

This is probably the biggest technical question you have.

**Yes, latency exists — but it doesn't make the project impossible.**

The trick is that you shouldn't try to process the entire video call through your backend.

Your architecture should look more like this:

```text
                 WEB APPLICATION

        User A                         User B
          │                              │
          │                              │
      Webcam 🎥                      Webcam 🎥
      Microphone 🎤                  Microphone 🎤
          │                              │
          └────────── WebRTC ────────────┘
                       │
                 DIRECT/P2P MEDIA
                       │
                 VIDEO + AUDIO
```

The actual call uses **WebRTC**.

Your server mainly handles things such as:

```text
User A
   │
   ├── Signaling
   │
   └──────────────→ User B

             Node.js
                │
          Signaling Server
```

The server doesn't need to continuously receive and retransmit the entire video stream.

# Then AI processing happens alongside the call

For speech:

```text
Microphone
     ↓
Speech recognition
     ↓
Partial transcript
     ↓
Caption
```

For signing:

```text
Camera
   ↓
Hand/pose landmarks
   ↓
Sign recognition model
   ↓
Recognized sign
   ↓
Caption
```

This can happen **locally in the browser** for some approaches.

That's actually something I'd strongly recommend for your project.

# You don't necessarily need to send the user's camera to an AI server

This is where technologies such as **MediaPipe** and **TensorFlow.js** become interesting.

For example:

```text
Webcam
   ↓
Browser
   ↓
MediaPipe
   ↓
Hand landmarks
   ↓
Your sign recognition model
   ↓
"HELLO"
```

The video doesn't necessarily have to leave the user's device for sign recognition.

That gives you:

* lower latency
* better privacy
* lower server costs
* less bandwidth
* better scalability

And it makes the project technically more interesting.

# But there is a BIG challenge with sign language

This is something I would **not underestimate**.

Recognizing:

> 👍 = "yes"

is relatively straightforward.

Real sign language isn't just a collection of static hand poses.

It involves:

* hand shape
* hand position
* movement
* orientation
* two hands
* facial expressions
* body posture
* context
* sequences of movements

So don't start by promising:

> **"Translate any sign language into English in real time."**

That would be an enormous ML project.

Instead, your MVP could support a **limited vocabulary**.

For example:

### MVP vocabulary

**Greetings**

* Hello
* Good morning
* Goodbye

**Basic conversation**

* Yes
* No
* Thank you
* Please
* Sorry
* Help
* I understand
* I don't understand

**Common needs**

* Water
* Food
* Bathroom
* Emergency
* Wait
* Come here

Then your model can recognize those specific signs.

# One architectural decision I'd make early

Don't make the backend:

```text
User
 ↓
Your server
 ↓
AI
 ↓
Your server
 ↓
Other user
```

for everything.

That's going to create unnecessary latency and infrastructure costs.

Instead:

```text
                    YOUR SERVER
                 ┌───────────────┐
                 │ Authentication│
                 │ Signaling     │
                 │ Users         │
                 │ Call metadata │
                 └───────┬───────┘
                         │
                 WebRTC signaling
                         │
        ┌────────────────┴────────────────┐
        ↓                                 ↓

      USER A                            USER B
 ┌──────────────┐                  ┌──────────────┐
 │ Camera       │                  │ Camera       │
 │ Microphone   │                  │ Microphone   │
 │              │                  │              │
 │ Sign AI      │                  │ Sign AI      │
 │ Speech→Text  │                  │ Speech→Text  │
 └───────┬──────┘                  └───────┬──────┘
         │                                  │
         └──────────── WebRTC ──────────────┘
```

That's a much more scalable architecture.

# And there's an even bigger opportunity

Because you're in South Africa, you could eventually make the project specifically support **South African Sign Language (SASL)** rather than building another generic American Sign Language demo.

That would give the project a much stronger identity:

> **A real-time accessible communication platform supporting South African Sign Language and live speech transcription.**

You could potentially work with Deaf users or organizations to build/validate the vocabulary and dataset.

That turns this from:

> "I built an AI webcam project."

into:

> **"I built a real-time communication platform designed to reduce communication barriers between Deaf/SASL users and hearing users."**

That's a **serious portfolio project**.

And I'd actually recommend building it in stages rather than trying to solve everything at once:

**Phase 1:** User accounts + contacts
**Phase 2:** 1-to-1 WebRTC video calls
**Phase 3:** Real-time speech → subtitles
**Phase 4:** Basic sign recognition (10–20 signs)
**Phase 5:** Sign → text subtitles during calls
**Phase 6:** Text → speech
**Phase 7:** SASL dataset/model expansion
**Phase 8:** Call history, accessibility settings, analytics, privacy controls

The important thing is that **Phase 2–3 already gives you a genuinely useful application**, while the sign-language AI can evolve independently instead of holding the whole project hostage.
